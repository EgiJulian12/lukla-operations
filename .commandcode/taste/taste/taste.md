# Taste
- Prefers spec-driven development where implementation strictly follows BRD/SRS docs referenced as source of truth (e.g. `@docs/...`). Confidence: 0.9
- Prefers project documentation kept as markdown files in `docs/` folder, including BRD/SRS specs and step-by-step local setup/run guides for onboarding to another device. Confidence: 0.85
- Communicates bilingually in English and Bahasa Indonesia — match the language of the request in replies; user messages are most often purely in Bahasa Indonesia (e.g. "apa saja kapabilitas client bot telegram?"). Confidence: 0.85
- Develops and runs the app locally on Windows (localhost, e.g. `http://127.0.0.1:8000`) rather than a deployed environment; for integrations needing public reachability, uses cloudflared tunnels (`cloudflared tunnel --url ...`, Cloudflare free tier) and follows the flow: tunnel up → set URL in `.env` → `config:clear` → re-register. Confidence: 0.85
- When providing configuration values (.env, tokens, URLs), give concrete copy-paste-ready literals tailored to the user's actual environment — placeholder text like `your-public-url` triggers follow-up "what do I put here" questions. Confidence: 0.8
- When the user reports an integration/runtime bug, they send a one-line symptom with no diagnostics and expect end-to-end self-investigation (DB queries, app log inspection, webhook/cURL probes) before replying — don't ask them for details first, just diagnose. Confidence: 0.8
- Bug fixes should end with a regression/feature test covering the failure case plus `pint --dirty`, with test counts and lint status reported in the summary. Confidence: 0.75
- User actively questions design defaults that seem inconvenient (e.g. "15 minutes is too short for the token URL?") — they expect the security/UX rationale explained plainly (why the limit exists, what breaks without it) plus concrete low-effort alternative options (e.g. env-configurable TTL) before anything is implemented. Confidence: 0.7
